# Bordkasse für Segeltörns — Claude Code Projekt

> Tool zur fairen Aufteilung gemeinsamer Kosten auf Segeltörns mit wechselnden Crews.
> Die Anwendung liegt in `webapp/` (die frühere Google-Sheets-/Apps-Script-Lösung wurde aus dem Repo entfernt, sie bleibt in der Git-Historie erhalten):
> - **Web-App** (`webapp/`) — Next.js + Supabase (selbst gehostet unter Coolify), Crew-fähig, Magic-Link-Auth, Realtime, PWA-Offline, Statistik, Audit-Log, automatische DSGVO-Löschung 30 Tage nach Törnende.

## Quick Context

**Wer baut das?** Jannik, Skipper, mehrere Törns pro Jahr, bis zu 12 Crewmitglieder pro Törn, Crew teils nicht-technikaffin (Eltern, Freunde).

**Was wird gelöst?** Faire Kostenaufteilung mit Berücksichtigung von:
- Teilweiser Anwesenheit (Crewmitglieder steigen verschieden ein/aus)
- Verschiedenen Aufteilungslogiken pro Ausgabe (gleichmäßig, nur Anwesende, zeitanteilig, individuell)
- Alkohol-Anteilen (Nicht-Trinker zahlen nicht mit)
- Vorauszahlungen außerhalb der Bordkasse (Gutschriften)

**Zielsetzung:** Smartphone-tauglich, einfach genug für jedes Crewmitglied, kein Login-Aufwand.

## Working Language

Deutsch. Alle Domain-Begriffe sind deutsch und sollen so bleiben:
- *Bordkasse* — die gemeinsame Kasse
- *Törn* — eine Segelreise
- *Besatzung* / *Crew* — die Mitsegler
- *An Bord* — anwesend auf dem Schiff
- *Zeitanteilig* — proportional zur Anwesenheitsdauer
- *Gleichmäßig* — alle gleich
- *Gutschrift* — Verrechnung außerhalb der Bordkasse
- *Schulden* — wer wem wie viel zahlen muss
- *Bilanz* — Saldo pro Person
- *Aufteilung* — Methode, wie eine Ausgabe verteilt wird

## Aufteilungs-Logiken (vier Varianten)

### 1. Gleichmäßig
Alle eingetragenen Crewmitglieder zahlen gleich viel — unabhängig von Anwesenheit.

```
Beispiel: 100€ Lebensmittel auf 10 Crew → jeder 10€
```

### 2. An Bord
Nur Personen, die am Tag der Ausgabe laut Besatzungs-Daten anwesend waren.

```
Beispiel: 80€ Restaurant am 08.04., Stephan kommt erst 10.04.
→ 9 Personen teilen 80€ → je 8,89€, Stephan 0€
```

### 3. Zeitanteilig
Proportional zur Anzahl Bord-Tage.

```
Beispiel: 210€ Sprit, 9 Personen à 11 Tage + Stephan 6 Tage = 105 Personentage
→ 11-Tage-Person: 22€, Stephan: 12€
```

### 4. Individuell
Nur explizit markierte Personen (Checkbox in der Eingabe).

```
Beispiel: 120€ Schwimmwesten für 3 Personen → je 40€
```

### Alkohol-Logik (modifiziert jede der 4 Aufteilungen)

Bei Ausgaben mit Alkohol-Anteil wird der Betrag aufgeteilt:
- Nicht-Alkohol-Teil: nach gewählter Aufteilung
- Alkohol-Teil: nur auf Personen mit "x" in Besatzung Spalte F (Alkoholtrinker)

```
Beispiel: 100€ Restaurant, 30€ davon Alkohol, "An Bord" alle 10 dabei, 3 Trinker
→ Nicht-Alkohol: 70€/10 = 7€ pro Person
→ Alkohol: 30€/3 = 10€ pro Trinker
→ Trinker: 17€, Andere: 7€
```

## Gutschrift-Logik

Gutschriften = Geld das außerhalb der Bordkasse fließt (z.B. Yacht-Vorauszahlung).

**Direkte Gutschrift** (Von Lucas → An Jannik, 240€):
- Lucas Saldo +240€ ("hat gegeben")
- Jannik Saldo -240€ ("hat erhalten")

**An Alle** (Von Lucas → An "Alle", 240€):
- Lucas hat 240€ direkt an die Crew gezahlt (z.B. seinen Yacht-Anteil nachträglich)
- Lucas: +240€
- Alle anderen Crewmitglieder bekommen anteilig zugerechnet: -240€/(N-1) je Person
- Saldo-Summe muss 0 bleiben

## Schulden-Algorithmus

Greedy-Matching für minimale Anzahl Überweisungen:
1. Bilanz-Salden lesen (`simplify_debts()` in SQL, TS-Mirror in `lib/calc/debts.ts`)
2. Schuldner (negativ) und Gläubiger (positiv) trennen, sortiert nach Höhe
3. Größter Schuldner zahlt an größten Gläubiger so viel wie möglich
4. Wenn einer "leer" ist, nächster Schuldner/Gläubiger
5. Maximal N-1 Überweisungen bei N Personen

## Bekannte Fallen (Berechnung)

**MATCH-Falle bei gleichen Saldenbeträgen** (stammt aus der früheren Sheets-Lösung, die aus dem Repo entfernt wurde):
- Ein Lookup per Betrag liefert immer den ersten Treffer → wenn 9 Personen je -10 € schulden, wird nur die erste Person gefunden.
- **Fix:** Schuldner/Gläubiger werden einzeln behandelt, nie über einen Betrags-Lookup; bei Gleichstand entscheidet ein deterministischer Tiebreak (Person-ID, siehe `simplify_debts()` Migration 0055 und `lib/calc/debts.ts`).

Der Zahlungstransfer nutzt `idempotency_key = <ID der Quell-Zahlung>` auf der bestehenden UNIQUE(trip_id, idempotency_key)-Spalte (0005) statt eines eigenen Check-before-Insert — echte DB-Garantie statt TOCTOU-Race, exakt das Muster aus `recordPayment`/`insertCredit`. **Ein erster Entwurf mit Check-before-Insert auf Betrag+Datum wurde beim Grill-Review verworfen:** er hätte zwei unterschiedliche, zufällig gleich hohe Zahlungen vom selben Tag als „schon übertragen" verwechselt und eine davon verschluckt (Geld verschwindet aus der Bilanz) — `idempotency_key` pro Quell-Zahlung ist präzise, weil jede Zahlung eine eigene ID hat. **Wichtige Architektur-Entscheidungen:**
- **Schreib-Pfad:** Server Actions schreiben mit dem Service-Role-Client (`lib/supabase/admin.ts`), weil das User-JWT in Next.js 16 Server Actions die DB nicht zuverlässig erreicht. Auth/Authz wandert dadurch ins App-Layer (`lib/auth/authz.ts` mit `requireAuth/Skipper/Admin/SkipperOrAdmin/Member` + `isEmailAllowedToSignIn`).
- **Lese-Pfad:** alle Lese-Queries laufen über `lib/supabase/read-client.ts:readClient()`. Für globale Admins (in `ADMIN_EMAILS`) liefert es den Service-Role-Client → bypass RLS, damit Admins fremde Törns sehen. Für alle anderen User → Cookie-basierter Client mit aktivem RLS.
- **Request-Dedup + Client-Router-Cache (Tab-Ladezeit):** Zwei zusammengehörige Hebel gegen langsame Tab-Wechsel. (1) **`React.cache()`** auf `getCurrentPerson` / `isAdmin` (`lib/auth/`) + `getTrip` / `getTripMembers` (`lib/queries/trips.ts`): Diese laufen pro Seitenaufruf vielfach, weil JEDE Lese-Query über `readClient()` → `isAdmin()` → `getCurrentPerson()` geht (eine einzelne Tab-Seite löst ~6, Layout + Page beim Törn-Öffnen ~11 Aufrufe aus). Ohne Memoisierung war das pro Render ~6–11× `auth.getUser()` (**Netz-Call zum Auth-Server in Frankfurt**) + doppelt so viele `persons`/`persons_private`-Queries — reine Identitätsauflösung, noch vor den eigentlichen Daten. `cache()` dedupliziert das pro Request auf 1× (Bonus: schließt eine Erst-Login-Race beim parallelen Anlegen der `persons`-Row aus). Gilt nur INNERHALB eines Requests — kein Cross-Request-Caching, keine Stale-Gefahr. (2) **`experimental.staleTimes.dynamic = 30`** (`next.config.ts`): besuchte (dynamische) Törn-Tabs bleiben 30 s im Client-Router-Cache → Hin-/Herwechseln ist sofort, ohne Server-Roundtrip. `dynamic` (nicht `static`) greift, weil die Nav-Links (`bottom-nav.tsx`) kein explizites `prefetch` setzen und alle Törn-Seiten dynamisch sind (Cookie-Auth → kein Prerender). Sicher für die Finanzdaten: `router.refresh()` (RealtimeTrip bei Fremd-Änderung) UND `revalidatePath` (eigene Schreib-Actions) verwerfen den Cache sofort; die 30 s greifen nur für reines Navigieren ohne zwischenzeitliche Mutation. Bewusst NICHT angefasst (Reserve, falls Prod weiter hakt): SW-Stale-While-Revalidate für RSC, aktives Tab-Prefetch, Lade-Splash (Letzterer adressiert nur den Kaltstart, nicht die Tab-Latenz).
- **Cookie-Binding in Auth-Routes:** `/auth/verify` (POST) erstellt zuerst die Redirect-Response, dann `createClient(response)`. Der Cookie-Adapter schreibt Set-Cookie direkt auf die Response, sonst landen Session-Cookies nicht im Browser (siehe Supabase Discussion #35615).

⚠️ **Ein Coolify-Deployment wendet KEINE Migrationen an — auch nicht das der Supabase-Ressource.** Das ist die naheliegende Fehlannahme („ich habe doch beide Instanzen deployt"): der Compose-Stack startet nur Container neu, und die Init-Skripte des `db`-Images laufen ausschließlich bei **leerem** Datenverzeichnis. Ein Redeploy lässt den Schemastand also exakt dort, wo er war. Nach dem Merge einer Migration ist der Push der **einzige** Schritt, der zählt; kontrollieren mit `select max(version) from supabase_migrations.schema_migrations`.

⚠️ **Der gefährliche Zwischenzustand ist der Versionsversatz, nicht das Fehlen an sich.** Coolify deployt bei Auto-Deploy sofort den neuen App-Code, während die DB noch das alte Schema trägt. Beobachtet bei Migration 0048: die neue Route erwartete von `purge_expired_trip_data` ein `(purged, failed)`, bekam aber die alte `integer`-Rückgabe — kein Absturz, aber `row?.purged` ist auf einer Zahl `undefined`, der Endpunkt meldete also **stumm `0/0`**, egal was tatsächlich passierte. Solche Signaturwechsel deshalb entweder tolerant lesen (wie dort mit `?? 0`) oder Migration **vor** dem App-Deploy einspielen.

**Migration ohne lokale DB-Verbindung einspielen** (wenn `supabase db push` gerade nicht geht): die Migrationsdateien liegen im öffentlichen Repo, und der `db`-Container hat `wget` **und** `curl` (geprüft). Als temporären Coolify Scheduled Task auf der Supabase-Ressource, Container `db`:

```
wget -qO- https://raw.githubusercontent.com/Jannik96D/bordkasse-public/main/webapp/supabase/migrations/<datei>.sql | psql -U postgres -d postgres -v ON_ERROR_STOP=1 --single-transaction -f -
```

`--single-transaction` + `ON_ERROR_STOP=1` sind wichtig: DDL ist in Postgres transaktional, die Migration greift damit ganz oder gar nicht. **Danach die Version nachtragen**, sonst hält der Ledger die Migration für ausstehend und `supabase db push` will sie erneut anwenden: `insert into supabase_migrations.schema_migrations(version,name) values('0048','purge_before_tranche_delete') on conflict do nothing` (Spalten: `version` NOT NULL, `statements`, `name`). Task hinterher löschen.

**Trockenlauf gegen echte Produktionsdaten** — die schnellste Diagnose für „Funktion schlägt fehl, aber warum": `psql -Atc "begin;select <funktion>(…);rollback;"` als temporärer Task. Liefert die vollständige Fehlermeldung inklusive `CONTEXT`, ohne eine Zeile zu verändern. Genau so wurde der 0048-Bug gefunden (und die Korrektur vorab an denselben Daten bewiesen). ⚠️ Niemals ohne `rollback;` — `purge_trip_data` löscht sonst wirklich.

**Env-Var-Status in Coolify** (Stand: 2026-08-05, per Coolify-API verifiziert — hier stehen bewusst nur **Namen + Flags, niemals Werte**; Snapshot bei Env-Änderungen aktualisieren). Coolify kennt zwei Flags pro Variable: **Buildtime** (wird als `ARG`/`ENV` in den Docker-Build gegeben) und **Runtime** (steht im laufenden Container):

| Variable | Flags | Notiz |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Buildtime + Runtime | Next backt `NEXT_PUBLIC_*` beim Build ein → Buildtime ist Pflicht |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Buildtime + Runtime | dito |
| `NEXT_PUBLIC_APP_ORIGIN` | Buildtime + Runtime | dito; App-Origin für Mail-Links **und** Origin-Fallback in `lib/auth/origin.ts` |
| `SUPABASE_SERVICE_ROLE_KEY` | **nur Runtime** | Service-Role, bypasst RLS — darf NIE Buildtime sein (landete sonst in Build-Args/-Logs) |
| `ADMIN_EMAILS` | nur Runtime | Admin-Whitelist |
| `CRON_SECRET` | nur Runtime | Cron-Auth (im Container als `process.env.CRON_SECRET` lesbar, 44 Zeichen — von den Scheduled Tasks genutzt) |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `MAIL_FROM` | nur Runtime | App-SMTP für Settlement-/Reminder-Mails. **Invite-/Magic-Link-Mails laufen NICHT hierüber**, sondern über GoTrue im Supabase-Stack (eigene SMTP-Vars dort) |
| `NEXT_PUBLIC_SITE_URL` | **NICHT gesetzt** | Magic-Link-Origin. Nicht nötig, weil `lib/auth/origin.ts` auf `NEXT_PUBLIC_APP_ORIGIN` zurückfällt (`||`, nicht `??` — siehe PR #239) |

Genau deshalb fällt es niemandem auf, denn alle Mails laufen weiter. Beim Nachtragen die **alten Vercel-Werte wiederverwenden**: neue Keys entwerten alle bestehenden Geräte-Abos (Versand 403). `NEXT_PUBLIC_VAPID_PUBLIC_KEY` braucht Buildtime + Redeploy, die anderen zwei nur Runtime |

**Konsequenzen fürs Debugging & Code-Review (wichtig!):**
- **`NEXT_PUBLIC_SITE_URL`/`NEXT_PUBLIC_APP_ORIGIN` sind seit dem Token-Guard sicherheitsrelevant**, nicht mehr nur Kosmetik: Next backt sie beim Build ein (auch in Server-Code), und daraus entsteht die Allowlist, gegen die `requestMayRedeemToken` entscheidet. Eine Domain-Änderung braucht deshalb einen **Rebuild**, kein Restart — sonst blockiert die alte Allowlist jeden Login mit `?auth_error=untrusted_host`. Notausgang, falls das doch passiert: beide Variablen aus den **Build**-Args entfernen und neu bauen; bei leerer Allowlist schaltet der Guard bewusst auf fail-open.
- **Coolify setzt „Available at Buildtime" standardmäßig für JEDE neu angelegte Variable** — auch für Secrets. Nach dem Anlegen aktiv kontrollieren und bei allem außer den `NEXT_PUBLIC_*`-Werten entfernen (Production- und Preview-Abschnitt werden getrennt verwaltet).
- **Preview-Deployments sind abgeschaltet** (`is_preview_deployments_enabled = false`). Im Preview-Scope liegt trotzdem eine vollständige Kopie der Variablen inklusive `SUPABASE_SERVICE_ROLE_KEY` — wer Previews je aktiviert, muss die vorher auf eine eigene Datenbank umbiegen, sonst hätte jeder PR-Build Service-Role-Zugriff auf die Produktionsdaten.
- **Ein nicht übergebener Docker-`ARG` wird beim `ENV`-Befehl zum LEEREN String, nicht zu `undefined`** — `process.env.A ?? process.env.B` fällt dagegen nicht zurück. Für Env-Fallback-Ketten deshalb `||` verwenden; für App-URLs in Mails gibt es dafür den zentralen Helper `appOrigin()` in `lib/auth/origin.ts` (nicht wieder `process.env.NEXT_PUBLIC_APP_ORIGIN ?? "…"` an der Aufrufstelle schreiben).
- **`curl` gibt es im App-Container NICHT** (`node:22-alpine`, empirisch geprüft). Für Kommandos in Scheduled Tasks `node -e "fetch(…)"` nutzen (so wie der `HEALTHCHECK`) oder BusyBox-`wget`; ein `command`-String über ~255 Zeichen lässt die Coolify-API mit HTTP 500 antworten.

**Secret-Scan:** `.github/workflows/secret-scan.yml` lässt bei jedem PR/Push auf `main` und wöchentlich **gitleaks** über die komplette Git-Historie laufen (gepinntes Release-Binary mit fester SHA-256, kein Drittanbieter-Action-Lizenzschlüssel; Konfiguration + Ausnahmen in `.gitleaks.toml`, erbt die Default-Regeln). ## Wichtige Prinzipien

**Pragmatik vor Perfektion.** Lieber eine einfache, robuste Lösung, die die Crew sofort nutzen kann, als ein perfektes System mit hoher Einstiegshürde.

**Deutsch ist verbindlich.** Auch in Kommentaren, Variablen optional englisch.

**Mobile zuerst.** Nicht-technikaffine Crew sitzt auf der Yacht mit Smartphone in der Hand, nicht am Laptop. Touch-Targets ≥ 40px Höhe, große Schrift, vertikal gestapelt.

**Fail-Safe.** Lieber ein Feld zu viel ausblenden als die Crew mit ungültigen Optionen verwirren. Die Server-Action validiert vor dem Speichern.

**Audit-Trail.** Transaktionen sind append-only — niemand löscht versehentlich Daten. Korrekturen über neue Gutschrift-Einträge.

**Barrierefreiheit mitdenken.** Bei jeder Änderung in der Web-App (`webapp/`) als Grundlinie WCAG 2.1 AA anstreben:
- Farbe ist nie alleiniger Informationsträger (z. B. Bilanz nutzt Farbe **und** „+/−"-Zeichen + Screenreader-Text).
- Jeder interaktive Bereich ist per Tastatur erreichbar und hat sichtbaren Fokus-Indikator (`focus:ring-2 focus:ring-primary/20` ist der Default).
- Custom-Komponenten folgen ARIA-Patterns (Listbox mit `aria-activedescendant` + Pfeil-Navigation, kein eigenes Wheel neu erfinden).
- Skip-Link in `app/layout.tsx` zum `#main-content`-Wrapper; `<html lang="de">` ist gesetzt.
- `prefers-reduced-motion` wird in `globals.css` respektiert — neue Animationen brauchen kein eigenes Handling.
- Touch-Targets mindestens 44 px (Default via `--spacing-touch` in `globals.css`).
- Form-Inputs haben Label-Verknüpfung (`htmlFor` / `id`); Fehler-Meldungen tragen `role="alert"`, Erfolgs-Meldungen `role="status"`.
- Bilder bekommen aussagekräftige `alt`-Texte, dekorative Icons `aria-hidden`.

Vor dem Mergen einer neuen Komponente kurz prüfen: kann ich nur mit Tab + Pfeiltasten alles bedienen? Sieht der Fokus-Ring sichtbar aus? Liest VoiceOver/TalkBack sinnvolle Texte?

**Grill-Pflicht vor Fertigmeldung.** Bevor eine nicht-triviale Code-Änderung (neues Feature, Bugfix, Migration, Refactor) als abgeschlossen gemeldet oder gemerged wird, muss sie zusätzlich zur eigenen Prüfung durch einen **unabhängigen Subagenten ohne Konversationskontext** adversarisch gegengelesen werden („Grillen") — nicht nur die eigene Selbstprüfung. Der Review-Agent bekommt ausschließlich den Diff/die betroffenen Dateipfade + genug Hintergrund, um kalt zu urteilen, und den Auftrag, aktiv nach Bugs, Security-Lücken und Edge Cases zu suchen statt Korrektheit anzunehmen. Trivial-Änderungen (Typo, Umbenennung, reine Doku) sind ausgenommen. Gefundene Probleme werden gefixt und wo sinnvoll durch einen Test abgesichert, bevor der Punkt als erledigt gilt. Hintergrund: ein solcher Grill-Durchlauf hat bereits einen Bug gefunden, den die Erstimplementierung UND ein `pnpm test`-Grünlicht übersehen hatten (fehlende Unterscheidung zwischen „anonymisiert" und „An Alle" bei Gutschriften nach dem DSGVO-Purge, siehe Migration 0046).
